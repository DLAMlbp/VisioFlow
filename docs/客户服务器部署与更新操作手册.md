# 图像智能处理服务：客户服务器部署与更新操作手册

> 文档版本：2026-09-11

本文是首次部署、日常更新、验证和回滚的统一主文档。已有生产服务器从受信任的 Windows 发布机更新时，优先使用仓库根目录的 `一键更新服务器.cmd`，具体参数见 [从本地安全更新生产服务器](local-production-deploy.md)；需要手工部署时按本文执行。只有交付方明确提供 Harbor 镜像时，才改用 [Harbor 首次部署说明](harbor-first-deployment.md)，不要在一次发布中混用 GHCR 与 Harbor 版本。

本文面向负责客户服务器上线与日常发布的运维人员。适用于当前仓库的生产架构：Web 网关、API、PostgreSQL、Redis、MinIO、Celery Beat 以及按处理阶段拆分的 Worker。

## 1. 发布原则

生产服务器只负责：

1. 拉取已经通过 CI 测试的版本化 Docker 镜像；
2. 执行数据库迁移；
3. 启动服务；
4. 执行健康检查；
5. 必要时回滚应用版本。

禁止在客户服务器执行 `docker build`、`npm run build` 或其他源码构建操作。禁止使用 `latest` 标签。发布版本必须使用完整 Git SHA、发布版本号或镜像 digest。

Git 仓库提供应用代码、数据库迁移和默认处理标准，但不包含以下运行数据：

- `.env.production` 中的密钥；
- 当前服务器数据库中的任务记录；
- 管理端后续修改的业务标准；
- 素材库图片和人工标签；
- MinIO 中的客户图片；
- Redis 运行状态。

客户需要独立环境时，默认采用“全新数据库 + 全新对象存储 + 独立密钥”。如果客户必须继承现有业务标准或素材库，应单独执行经过授权的数据迁移，不能仅靠 Git 完成。

## 2. 架构与网络

```text
客户调用方/浏览器
        |
      HTTPS
        |
外部负载均衡或反向代理
        |
Web :8088 -> API :8000
                    |-- PostgreSQL
                    |-- Redis/Celery
                    |-- MinIO
                    |-- AI 接口（出站 HTTPS）
                    `-- 客户回调地址（出站 HTTPS）
```

建议准备两个域名：

| 用途 | 示例 | 转发目标 |
|---|---|---|
| Web 与接口入口 | `image-api.customer.example` | `127.0.0.1:8088` |
| 文件下载入口 | `image-files.customer.example` | `127.0.0.1:19001` |

网络要求：

- 入站只开放 `22`（限制管理员 IP）、`80` 和 `443`；
- `8088`、`19001` 不应直接暴露到公网，应通过安全组/防火墙限制；
- 不对公网开放 PostgreSQL、Redis 或 MinIO 内部端口；
- 允许服务器出站访问 `ghcr.io`、AI 服务地址、DNS/NTP 和客户回调域名的 HTTPS 端口；
- 客户回调必须使用 HTTPS，且回调域名必须写入 `CALLBACK_ALLOWED_HOSTS`；
- 服务器必须启用时间同步，否则回调签名时间校验可能失败。

外部代理必须保留原始 `Host` 和查询参数。文件域名必须与 `S3_PUBLIC_ENDPOINT` 完全一致，否则 MinIO 签名下载地址可能失效。

## 3. 服务器要求

当前生产 Compose 为 CPU 部署，并配置了多个独立 Worker。建议资源：

| 项目 | 建议值 |
|---|---|
| 操作系统 | Ubuntu Server 22.04/24.04 LTS，x86_64 |
| CPU | 建议 12 核以上，最低 8 核需压测确认 |
| 内存 | 建议 24–32 GiB，不建议低于 16 GiB |
| 系统盘 | SSD，至少 100 GiB；图片量大时单独规划 Docker/MinIO 数据盘 |
| Swap | 仅作故障缓冲，不能代替物理内存 |
| Docker | Docker Engine 与 Docker Compose v2 插件 |

当前 CI 产物按 GitHub x86_64 Runner 构建。ARM 服务器必须先扩展 CI 为多架构镜像，不能直接部署现有镜像。

安装 Docker 时使用 Docker 官方仓库的受支持安装方式。完成后验证：

```bash
docker version
docker compose version
docker info
```

## 4. GitHub/CI 发布镜像

仓库工作流为 `.github/workflows/publish-images.yml`，会执行：

```text
后端校验与测试 -> 构建 API 镜像 -> 推送 GHCR
前端测试与构建 -> 校验 Nginx -> 构建 Web 镜像 -> 推送 GHCR
```

每次准备发布时：

1. 将经过审核的代码合并到 `main`；
2. 打开 GitHub 仓库的 **Actions**；
3. 选择 **Test and publish production images**；
4. 如果提交未自动触发，使用 **Run workflow** 手动触发；
5. 必须等待 `api` 和 `web` 两个 Job 全部成功；
6. 记录该次提交的完整 40 位 Git SHA，例如 `0123456789abcdef0123456789abcdef01234567`。

CI 会生成：

```text
ghcr.io/zuixi01/tuxiangshibie-api:FULL_GIT_SHA
ghcr.io/zuixi01/tuxiangshibie-web:FULL_GIT_SHA
```

CI 失败、任一镜像不存在或只有 `latest` 标签时禁止部署。

如果 GHCR 包是私有的，在客户服务器创建只具备 `read:packages` 权限的部署凭据，不要使用开发人员的个人密码：

```bash
read -s GHCR_TOKEN
printf '%s' "$GHCR_TOKEN" | docker login ghcr.io -u GITHUB_USER --password-stdin
unset GHCR_TOKEN
```

## 5. 首次部署

### 5.1 创建部署目录

以下服务器命令默认在受控的 root 管理会话中执行。管理员仍使用个人 SSH 公钥登录，不共享 root 私钥或密码：

```bash
ssh ADMIN_USER@CUSTOMER_SERVER
sudo -i
umask 077
```

```bash
sudo install -d -m 750 /opt/image-intelligence
cd /opt/image-intelligence
```

从可信工作站通过 SSH 只上传生产 Compose 文件：

```bash
scp docker-compose.prod.yml ADMIN_USER@CUSTOMER_SERVER:/tmp/docker-compose.prod.yml
ssh ADMIN_USER@CUSTOMER_SERVER
sudo -i
sudo install -o root -g root -m 640 /tmp/docker-compose.prod.yml /opt/image-intelligence/docker-compose.prod.yml
```

不要把本地 `.env`、`.env.production`、私钥或测试数据提交到 Git，也不要通过聊天工具传递。

### 5.2 生成独立密钥

每个字段必须生成不同值。建议使用只含十六进制字符的随机值，避免数据库 URL 转义问题：

```bash
openssl rand -hex 32  # API_KEY
openssl rand -hex 32  # INTEGRATION_API_KEY
openssl rand -hex 32  # AUTH_SESSION_SECRET
openssl rand -hex 32  # CALLBACK_SIGNING_SECRET
openssl rand -hex 32  # AI_CONFIG_ENCRYPTION_KEY
openssl rand -hex 32  # POSTGRES_PASSWORD
openssl rand -hex 32  # MINIO_ROOT_PASSWORD/S3_SECRET_KEY
```

密钥生成后放入密码管理系统，不要打印到部署日志。

### 5.3 创建 `.env.production`

在服务器执行：

```bash
cd /opt/image-intelligence
sudo install -o root -g root -m 600 /dev/null .env.production
sudoedit .env.production
```

以下为必填骨架。所有大写占位值都必须替换：

- `API_KEY` 仅用于受信任的服务端管理调用和首次管理员初始化，Web 网关不得向浏览器注入；`INTEGRATION_API_KEY` 专供客户服务端调用，两者不要共用；
- `AUTH_SESSION_SECRET` 用于登录会话的 CSRF 校验，必须独立生成并在所有 API 实例间保持一致；
- `AI_TAGGING_API_KEY` 必须能够调用当前代码锁定的 AI 服务和模型；
- `AI_CONFIG_ENCRYPTION_KEY` 一旦投入使用必须长期保存，丢失后 Redis 中加密的 AI 配置无法解密；
- `CALLBACK_ALLOWED_HOSTS` 填主机名，不填路径；多个域名使用英文逗号分隔，禁止 `*`；
- `API_IMAGE`、`API_GATEWAY_IMAGE`、`CLASSIFICATION_IMAGE` 与 `RENDER_IMAGE` 必须指向同一个 API 版本；
- 素材匹配只保留自动二元判定；上线前使用离线标注集完成采用线校准，线上不提供 Shadow 或人工改判路径。

```bash
cd /opt/image-intelligence
sudo chown root:root .env.production docker-compose.prod.yml
sudo chmod 600 .env.production
sudo chmod 640 docker-compose.prod.yml
docker compose --env-file .env.production -f docker-compose.prod.yml config --quiet
```

### 5.4 首次启动

启动前执行资源检查：

```bash
uptime
free -h
swapon --show
df -h
df -ih
docker system df
```

满足以下任一条件时停止部署：磁盘或 inode 使用率达到 85%；可用磁盘不足 10 GiB 或容量的 20%；可用内存不足 2 GiB 或总内存的 25%；5 分钟负载高于 CPU 核心数；内核日志存在 OOM、I/O 或文件系统错误。

确认资源正常后执行：

```bash
cd /opt/image-intelligence
docker compose --env-file .env.production -f docker-compose.prod.yml pull
docker compose --env-file .env.production -f docker-compose.prod.yml up -d --remove-orphans
docker compose --env-file .env.production -f docker-compose.prod.yml ps --all
```

`migrate` 会自动执行 `alembic upgrade head`，`minio-init` 会创建私有 Bucket。这两个一次性容器执行成功后显示 `Exited (0)` 属于正常现象。

数据库首次初始化后，使用服务端 `API_KEY` 创建唯一的首个管理员。接口只在系统尚无管理员时生效，密码至少 10 位；完成后由该管理员在 Web 的“账号管理”中管理其他账号：

```bash
curl --fail --request POST http://127.0.0.1:8088/api/v1/auth/bootstrap \
  --header "X-API-Key: 替换为服务端API_KEY" \
  --header "Content-Type: application/json" \
  --data '{"username":"admin","display_name":"系统管理员","password":"替换为高强度初始密码","role":"admin"}'
```

登录页同时开放自助注册。用户可使用普通用户名或邮箱作为登录账号，注册成功后固定为“操作员”角色并直接进入工作台，不能自行注册为管理员。默认每个来源 IP 每分钟最多注册 5 次，可通过 `AUTH_REGISTRATION_RATE_LIMIT_PER_MINUTE` 调整。

### 5.5 配置 HTTPS 入口

建议在客户已有负载均衡、API Gateway 或反向代理上终止 HTTPS。下面是同机 Nginx 的最小转发示例，证书配置由客户证书平台管理：

```nginx
server {
    listen 443 ssl http2;
    server_name image-api.customer.example;

    client_max_body_size 512m;
    location / {
        proxy_pass http://127.0.0.1:8088;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
        proxy_read_timeout 300s;
    }
}

server {
    listen 443 ssl http2;
    server_name image-files.customer.example;

    client_max_body_size 512m;
    location / {
        proxy_pass http://127.0.0.1:19001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
        proxy_request_buffering off;
        proxy_buffering off;
    }
}
```

配置后执行 Nginx 配置检查并从外部网络验证两个域名。不要因为代理已配置就开放 `8088` 或 `19001` 的公网安全组规则。

### 5.6 首次验收

```bash
curl --fail --silent http://127.0.0.1:8088/health
curl --fail --silent http://127.0.0.1:8088/health/ready
docker compose --env-file .env.production -f docker-compose.prod.yml ps --all
docker compose --env-file .env.production -f docker-compose.prod.yml logs --since 10m --tail 200 api worker-control worker-callback
```

`/health/ready` 必须返回所有项目为 `ok`。然后完成一组小流量端到端测试：

1. 通过 HTTPS 登录 Web 工作台，确认管理员可以维护账号，操作员看不到账号管理入口；
2. 使用 1–3 张测试图片调用客户接口；
3. 确认任务完成且无节点长时间卡住；
4. 确认回调签名、幂等键和 `objectKey` 正确；
5. 确认 `selected` 图片的 `enhancedUrl` 可下载；
6. 确认 `rejected` 图片返回 `enhancedUrl: null`；
7. 确认客户回调接收端只入库一次。

通过小流量验收后再开放正式流量。

## 6. 日常更新流程

### 6.1 发布前确认

1. CI 的 API/Web Job 全部为绿色；
2. 新 API 和 Web 镜像都存在；
3. 已记录新版本完整 Git SHA；
4. 当前没有正在处理的客户任务；
5. 没有其他构建、备份或迁移任务；
6. 已确定上一个健康版本，作为回滚目标。

查看 Celery 活动任务：

```bash
cd /opt/image-intelligence
docker compose --env-file .env.production -f docker-compose.prod.yml exec -T worker-control \
  celery -A src.workers.celery_app inspect active
docker compose --env-file .env.production -f docker-compose.prod.yml exec -T worker-control \
  celery -A src.workers.celery_app inspect reserved
```

如果还有活动任务，先停止客户入口流量并等待任务自然结束。不要在处理中强制替换 Worker。

### 6.2 强制前置检查

```bash
cd /opt/image-intelligence
uptime
free -h
swapon --show
df -h
df -ih
docker system df
docker compose --env-file .env.production -f docker-compose.prod.yml ps
journalctl -k -b 0 --since '-2 hours' --no-pager | \
  grep -iE 'oom|out of memory|killed process|panic|i/o error|ext4.*error|xfs.*error' || true
```

资源触及首次部署章节中的安全阈值时，立即停止发布，不自动清理镜像、不自动重试。

### 6.3 备份当前版本和数据库

```bash
cd /opt/image-intelligence
DEPLOY_ID="$(date -u +%Y%m%dT%H%M%SZ)"
sudo install -d -m 700 ".deployments/$DEPLOY_ID"
sudo cp --preserve=mode,ownership .env.production ".deployments/$DEPLOY_ID/env.production"
sudo cp --preserve=mode,ownership docker-compose.prod.yml ".deployments/$DEPLOY_ID/docker-compose.prod.yml"
sudo chmod 600 ".deployments/$DEPLOY_ID/env.production" ".deployments/$DEPLOY_ID/docker-compose.prod.yml"

docker compose --env-file .env.production -f docker-compose.prod.yml \
  exec -T postgres sh -c 'exec pg_dump -Fc -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  > ".deployments/$DEPLOY_ID/postgres.dump"
chmod 600 ".deployments/$DEPLOY_ID/postgres.dump"
docker compose --env-file .env.production -f docker-compose.prod.yml \
  exec -T postgres pg_restore -l < ".deployments/$DEPLOY_ID/postgres.dump" > /dev/null
```

数据库备份必须同步到服务器之外的受控备份位置。MinIO 数据应使用对象存储复制、版本控制或数据盘快照进行异地备份。

### 6.4 切换到新镜像

编辑 `.env.production`，将以下五项全部切换到同一个新版本：

```dotenv
API_IMAGE=ghcr.io/zuixi01/tuxiangshibie-api:NEW_FULL_GIT_SHA
API_GATEWAY_IMAGE=ghcr.io/zuixi01/tuxiangshibie-api:NEW_FULL_GIT_SHA
CLASSIFICATION_IMAGE=ghcr.io/zuixi01/tuxiangshibie-api:NEW_FULL_GIT_SHA
RENDER_IMAGE=ghcr.io/zuixi01/tuxiangshibie-api:NEW_FULL_GIT_SHA
WEB_IMAGE=ghcr.io/zuixi01/tuxiangshibie-web:NEW_FULL_GIT_SHA
```

验证并发布：

```bash
cd /opt/image-intelligence
docker compose --env-file .env.production -f docker-compose.prod.yml config --quiet
docker compose --env-file .env.production -f docker-compose.prod.yml pull
docker compose --env-file .env.production -f docker-compose.prod.yml up -d --remove-orphans
docker compose --env-file .env.production -f docker-compose.prod.yml ps --all
curl --fail --silent http://127.0.0.1:8088/health/ready
```

数据库迁移失败、容器反复重启、就绪接口不是 HTTP 200 或关键 Worker 不健康时，本次发布判定失败，不得反复执行相同命令。

### 6.5 发布后验证

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml logs \
  --since 10m --tail 200 api worker-control worker-callback worker-classification worker-beautify-plan
```

确认：

- `api`、Web 和所有长期运行 Worker 为 `healthy`；
- `migrate`、`minio-init` 为 `Exited (0)`；
- `/health/ready` 返回 `ready`；
- 没有持续出现 OOM、数据库连接、Redis、对象存储或 AI 鉴权错误；
- 用 1–3 张图片完成一次接口、处理、下载和回调验收；
- 将部署时间、Git SHA、镜像引用、执行人和验收结果记录到发布记录。

## 7. 回滚

应用健康检查失败时，恢复发布前快照。快照中的五个镜像变量必须一起恢复，禁止只回滚 Web 或部分 Worker：

```bash
cd /opt/image-intelligence
sudo cp --preserve=mode,ownership ".deployments/PREVIOUS_DEPLOY_ID/env.production" .env.production
sudo cp --preserve=mode,ownership ".deployments/PREVIOUS_DEPLOY_ID/docker-compose.prod.yml" docker-compose.prod.yml
docker compose --env-file .env.production -f docker-compose.prod.yml pull
docker compose --env-file .env.production -f docker-compose.prod.yml up -d --remove-orphans
docker compose --env-file .env.production -f docker-compose.prod.yml ps --all
curl --fail --silent http://127.0.0.1:8088/health/ready
```

数据库迁移默认要求向前兼容。应用回滚时不要自动执行 `alembic downgrade`。如新迁移造成不兼容，必须先评估数据损失，再由数据库负责人单独批准恢复数据库备份。

禁止在回滚时执行 `docker system prune`、删除数据卷、重启 Docker 或重启服务器。

## 8. 业务标准和素材库迁移

全新部署会通过 Alembic 创建数据库结构并写入代码版本自带的默认标准，但不会自动复制现有生产环境后续编辑的数据。

如果客户需要和现有环境保持相同处理效果，应明确迁移范围：

| 数据 | 是否来自 Git | 建议方式 |
|---|---|---|
| 应用代码与数据库结构 | 是 | CI 镜像 + Alembic |
| 代码版本内置默认标准 | 是 | Alembic 初始化 |
| 管理端后续修改的标准 | 否 | 经审核后通过管理端重建或专项导出/导入 |
| 素材组、人工标签、素材元数据 | 否 | 专项数据库迁移 |
| 素材原图和缩略图 | 否 | MinIO/对象存储同步 |
| 历史客户图片和任务 | 否 | 默认不迁移，确需迁移必须取得数据授权 |
| API Key、AI Key、回调密钥 | 否 | 客户环境重新生成，禁止复制 |

素材库数据库记录和对象存储文件必须一起迁移，不能只复制其中一侧。迁移完成后应重新核对素材数量、对象存在性、向量版本和抽样匹配结果。

## 9. 常见故障处理

### `/health/ready` 返回 503

查看就绪结果和有限量日志：

```bash
curl -sS http://127.0.0.1:8088/health/ready
docker compose --env-file .env.production -f docker-compose.prod.yml logs --since 10m --tail 200 api
```

根据 `database_schema`、`redis`、`object_storage`、`configuration` 中失败的项目处理，不要盲目重启全部服务。

### GHCR 拉取失败

检查镜像 SHA 是否真实存在，以及部署令牌是否具备 `read:packages`。不要改用 `latest` 绕过。

### AI 节点立即失败

核对 `AI_TAGGING_API_KEY` 是否有效、服务器能否出站访问 AI 服务、账户是否限额。当前流水线按失败熔断设计，不应无限重试。

### 回调失败

核对客户回调 HTTPS 地址、`CALLBACK_ALLOWED_HOSTS`、DNS、证书、签名密钥及客户接口响应时间。客户接收端应在 15 秒内完成必要校验和幂等落库并返回 HTTP 2xx，耗时业务应转入客户内部异步队列。

### 主机在发布或运行期间失联

恢复连接后先检查：

```bash
uptime
free -h
df -h
df -ih
docker compose --env-file .env.production -f docker-compose.prod.yml ps --all
journalctl -k -b -1 --no-pager | grep -iE 'oom|out of memory|killed process|panic|i/o error|ext4|xfs' || true
```

如果主机没有重启，将 `-b -1` 改为 `-b 0`。查明原因前禁止再次发布。
