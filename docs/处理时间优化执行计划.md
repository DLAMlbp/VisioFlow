# 图片处理时间优化执行计划

日期：2026-09-07

状态：P0 的版本、既有测试与接口基线已采集；按后续指示完成了默认关闭的 AI 公平调度本地候选。人工质量基准与完整链路验收尚未通过，未发布性能改动。候选细节见《公平调度候选说明》。

范围：在维持图片质量、分类过滤准确度、素材匹配与标签准确度的前提下，降低处理延迟并提高持续产出。鉴权问题不在本计划范围内。

## 1. 执行结论

采用“固定质量基线 → 消除重复计算与渲染冷启动 → 改善 AI 调度 → 入口逐档提速”的顺序。

第一轮保持 AI 模型、提示词、图片输入尺寸、分类与匹配阈值、美化参数、图片编码质量不变。分类与美化规划合并属于改变模型决策方式的实验，不进入第一轮生产发布。

不承诺有限测试能够证明所有未来输入质量绝对不变；用确定性回放、人工标注集、真实模型对照与上线抽检共同约束风险。任何质量闸门不通过，取消该项上线，不以耗时收益抵消质量退化。

## 3. 执行分工及顺序

角色：开发执行实现与测试，验收人负责标注和争议裁决，发布执行人负责资源检查、灰度和回滚。同一人可以兼任，但人工质量裁决需要用户或业务验收人确认。

| 阶段 | 工作量估计 | 交付物 | 进入下一步条件 |
| --- | --- | --- | --- |
| P0 | 0.5–1 工作日 | 固定数据集、基线报告、版本清单、指标定义 | 标注与成功基线可用 |
| P1 | 1–2 工作日 | 重复向量修正候选、渲染回收实验报告 | 确定性结果与质量闸门通过 |
| P2 | 1–2 工作日 | AI 等待原因统计、公平调度候选 | 无饿死、超额、重复调用或完成丢失 |
| P3 | 0.5–1 工作日开发，加观察窗口 | 入口 4/5 档容量报告 | 持续产出提升且队列稳定 |
| P4，可选 | 另行估算 | 规划缓存或合并请求实验报告 | 先证明收益，再单独批准上线 |

总计约 3–6 个工作日加发布观察时间；这是工作量估计，不是系统耗时或保证交付日期。

## 4. P0：冻结基线和质量标准

### 4.1 固定版本和数据

- 记录每个实际运行服务的镜像 ID/digest、代码版本、处理规则及美化/水印/素材库配置版本。线上存在过不同服务使用不同版本的情况，禁止用工作区 HEAD 代替运行版本。
- 在隔离测试环境建立已知可运行的基线版本；不直接用最新 HEAD 覆盖线上行为。
- 建立 140 张人工标注基准集：40 张明确分类样本、40 张易混淆或易误过滤样本、20 张水印/Logo 样本、20 张素材匹配边界样本、20 张方向/大图/低照度/文件异常样本。明确类别与测试目的；另做原始字节完全相同的重复提交测试，不伪装成新的独立样本。
- 每类样本同时覆盖应通过和应拒绝的情况；记录正确分类、过滤结论、允许的匹配资产/标签集合、需保留的图片区域。
- 测试基线与候选时冻结素材库快照。库变更、阈值变更、模型供应方变化的结果不归入代码优化收益。
- 单独统计冷启动、热运行、缓存命中、缓存未命中；禁止混合后报告一个平均值。

### 4.2 测量口径

从现有日志与数据中提取，不先建设大范围计时系统：

- 客户端首次提交 → 接口接收：入口等待与上传成本。
- 接口接收 → 首张结果就绪、批次业务完成：后端延迟。
- 业务完成 → 回调送达：通知延迟。
- AI 等待、实际请求、worker 执行时长：分别统计，不相加重复计算。
- 成功产出数、输入数、通过率、失败率、每张输入/通过图片的 AI 请求数。
- 等待中的任务数量及最老任务年龄；空任务、重复任务与真实处理任务分开。
- 确认数据库字段是否使用事务起点时间。已有字段出现过起止差与 AI duration 不一致，不能直接相减作为精准执行耗时。

运行 3 次顺序交替的基线/候选配对测试；第一次冷运行单列。真实模型测试使用同输入、同提示词、同供应商配置，记录测试时段。对相同请求输入也有模型输出波动的样本，单独裁决，不把波动自动归因于代码。

### 4.3 质量闸门

| 项目 | 必须满足的条件 |
| --- | --- |
| 确定性回放 | 对固定 AI 响应与固定模型推理结果，分类/过滤、选择资产、继承标签、最终完成状态完全一致；同运行环境的像素输出一致 |
| 分类与过滤 | 标注集无新增严重误放行、误拒绝或错分类；逐类准确率不得低于基线；所有新增错误必须逐例处理 |
| 素材匹配 | 正确匹配与正确拒绝指标不得降低；边界样本无新增错误标签；禁止调低相似度门槛换速度 |
| 图片质量 | 不新增错旋转、明显颜色/曝光变化、纹理损失、水印残留或遮挡扩大；执行既有验收规则和人工盲审 |
| 任务完整性 | 相同业务输入处理数量一致；不能以提前结束、跳过分析或减少成功图片数换取提速 |
| 失败语义 | 不新增重复执行副作用、重复回调、卡死、超时恢复失效；拒绝图片不算系统故障 |

若有限样本无退化，仅说明通过该次验收；发布后继续抽检。样本覆盖不足时扩充基准集，不放宽门槛。

## 5. P1-A：移除同输入的重复向量计算

代码定位：src/workers/matching.py、src/repositories/jobs.py、src/workers/render.py、src/services/jobs/progression.py。

1. 核对运行镜像中临时与最终向量的实际输入，明确业务语义是原图特征还是交付图特征。现有本地代码两者均选 thumbnail_object_key，但仓库注释又提及交付图，不能只依据注释修改。
2. 第一轮严格保持当前已验收的输入语义。只有输入字节哈希、模型版本、预处理版本和维度都一致，才允许保留临时向量并转为最终可用状态。
3. 输入发生变化、临时向量失败或版本不符，沿原路径生成最终向量；不以源文件名/对象路径相同判定相同内容。
4. 使用数据库条件更新保证幂等；覆盖“渲染先结束”“向量先结束”“重复消息”“取消/失败”“同时竞争最终匹配”情形。
5. 不修改素材相似度、置信度、标签来源或最终匹配完成条件。若业务确认需要改用交付图，另立准确度变更，不并入本次无损优化。

验收：固定输入的向量数值、匹配结果与标签一致；受影响图片仅进行一次实际推理；无双重计数、重复回调或无法结束。预期节省约一次 0.47 秒任务及其排队，最终延迟收益以关键路径实测为准。

回退：保留旧重算路径，候选采用默认关闭的开关；开关名称与部署方式由该项实现明确记录，不能把计划中的开关当作当前已存在。回退不删除已有向量或结果。

## 6. P1-B：渲染回收频率 3→10 的对照实验

代码/配置定位：docker-compose.prod.yml 中 worker-render；相关运行时为 render.py 及 OCR/Logo 模型加载器。

1. 在测试环境保持并发 1、CPU/内存上限、输入图片与编码参数不变，只把 --max-tasks-per-child=3 改为 10。
2. 连续运行至少 100 次渲染，覆盖有/无 Logo、复杂文字和大图；先完成基线，再完成候选，分别记录每个进程第 N 张的耗时和内存。
3. 测量整个容器内存，不能仅看单个 Python 进程 RSS；进程退出与重建期间也计入峰值。
4. 候选不得超过容器限制的 80% 峰值，不得出现随每轮回收周期持续抬高的内存基线；如出现则保持 3，不以硬上限临界值继续测试。
5. 不预设 10 一定成功，不直接增加 render 并发，不同时延长 inpaint 回收周期。

验收：图片结果和人工质量验收通过，渲染平均耗时目标降低至少 10%，P95 不上升，资源闸门通过。理论摊销改善约 0.76 秒/张，不承诺批次同比下降。

回退：将 worker-render 配置恢复到该服务原快照中的 --max-tasks-per-child=3 和原镜像版本，通过标准发布替换服务；不重启 Docker 或主机。

## 7. P2：先证实等待原因，再改善调度

代码定位：src/services/images/vision_rate_limit.py、src/services/jobs/dispatch.py、src/workers/analysis.py。

### 7.1 先完成窄范围诊断

利用已有 Lua 返回的限流、在途、冷却信息，必要时只补充本项所需的等待原因计数、operation 和 task/image ID 关联；不输出提示词、图片地址、参数或凭据。只有执行本计划的实现阶段才添加这些字段。

分别统计：RPM 耗尽、全局并发占满、429 冷却和 worker 自身积压。多个条件同时成立时允许多标签，不强行归为一种。

### 7.2 第一轮保持额度不变

- 保持 24 RPM、全局并发 5、分类/规划/分析 worker 并发 4/2/2。
- 在原调度入口实现 Redis 原子领取的公平等待顺序：先按等待年龄，再对三个阶段轮转；空阶段的机会可借用，避免硬预留造成闲置。
- 新到任务不得越过已等待任务直接抢占空位。初始采用公平顺序，不直接设置无限制的“即将完成优先”，以免饿死新分类。
- 等待条目使用独立 attempt ID、心跳/过期清理；取消、异常、进程丢失时可回收。完成后释放在途名额；等待名额和在途名额明确分开。
- 保留既有冷却与容量降低规则；重试、超时、失败行为不因调度改造而隐式变化。
- 第一轮不同时重构 Celery 任务挂起/重新发布。释放整个 worker 的等待占用涉及恢复租约与幂等，应单独验证后再考虑，避免把小优化扩大成高风险队列改造。

必要验证：并发领取不能超额；排队任务不饿死；worker 丢失后不永久占位；Redis 重连后无重复请求；取消任务不继续调用；没有内容分析完成但批次无法汇合的情况。

验收：同负载下最老等待年龄及批次 P95 改善；任何阶段 P95 不因转移拥塞而明显恶化；AI 上游请求错误率不升。批次 P95 改善不足 10% 时报告真实结果，不为达到数字强行扩大配额。

### 7.3 并发 5→6 是条件分支

只有同时满足以下条件才试验：证据显示主要卡在并发而非 RPM；上游已确认允许更高并发；资源达到安全阈值；公平调度无正确性问题。

仅在隔离测试中 5→6，保持 RPM=24，先不改 worker 数。若 RPM 等待或错误增加、成功产出未增加，恢复 5。不得直接跳到 8 或 10。生产容量决定必须基于实际供应商限额和候选实测，计划不假定上游额度可以提高。

## 8. P3：入口额度分档提速

配置定位：INTEGRATION_RATE_LIMIT_IMAGES_PER_MINUTE。这个参数已经存在；突发容量保持 20、队列门槛保持 100、最大任务图片数保持现状。

| 档位 | 持续额度 | 10 张补充额度时间 | 前置条件 |
| --- | --- | --- | --- |
| 基线 | 3 张/分钟 | 200 秒 | 现状 |
| A | 4 张/分钟 | 150 秒 | P0 质量通过，资源与容量测试通过 |
| B | 5 张/分钟 | 120 秒 | A 稳定，规划与分析仍有余量 |
| 后续实验 | 6 张/分钟 | 100 秒 | 本计划不默认上线，另做下游容量验证 |

执行方法：

1. 测试环境每档做两个负载窗口：接近全部通过、接近历史约 70% 通过。固定 batch=10，连续提交 20 批，并在输入结束后等全部排空。额外做一次初始突发 20 张检查。
2. 上游按 Retry-After 等待，保留幂等请求标识；不要循环新建相同批次。客户端传输异常后先确认是否已创建任务，再决定重试。
3. 每分钟记录成功完成数、等待数、最老任务年龄和资源；同时保留所有图片的质量结果。清楚区分过滤拒绝与系统失败。
4. 排除启动阶段后，最后 30 分钟等待队列不能持续增长；最老等待年龄不得不断增长；排空时间不能一档比一档无限拉长。
5. 同分布下候选成功产出应明显增加；单批 P95 不得高于基线 10% 以上。若入口放行增加但产出不增或尾延迟越界，退回上一档。
6. 测试通过后上线 A 档，在自然业务下至少观察 24 小时。只有覆盖足量真实成功图片且无退化，再决定 B 档。没有流量不等于验证通过。

注意：美化规划两个并发槽位按历史请求均值推算只有约 5.25 张通过图片/分钟的理想能力，尚未扣除调度等待。全通过负载下不能据此承诺入口 5 一定稳定。

回退：B→A 或 A→3，恢复发布快照中的入口参数；已有队列按原流程处理，不取消或删除正在运行的任务。

## 9. P4：有条件的更大幅提速实验

### 9.1 美化规划缓存

先只在测试环境评估，不在 P1 默认上线。相同图片也可能由于质量指标、尺寸、规则版本或输入上下文不同而需要不同规划。

- 缓存键涵盖访问范围/租户、实际送模图片哈希、完整规划输入上下文、模型标识与已知版本、系统和用户提示词哈希、采样及响应结构配置、规则和美化配置版本。
- 仅缓存完成结构校验与策略校验的成功规划；失败、截断、低可信结果不缓存。
- 命中后仍执行当前策略校验与实际美化验收；有任何版本或上下文变化则不命中。
- 使用访问隔离、按现有数据保留期设置有效期和版本失效机制；供应商模型版本无法可靠固定时，不承诺跨期结果等价。
- 同时报告冷缓存和热缓存收益、真实重复率。重复率低时优先停止该项，避免为低命中率引入维护成本。

质量验收通过时，命中图片可省掉一次约 21 秒的请求及等待；平均收益取决于命中率和关键路径。不能把所有图片按缓存命中估算。

### 9.2 分类与美化规划合并

这是独立质量实验，第一轮明确不上线。

### 10.3 发布方式

- 测试和镜像构建均在本地或 CI 完成；服务器不执行任何构建。
- 每个阶段独立提交、独立不可变镜像与配置版本。先部署上一阶段并观察，再推进下一阶段。
- 发布前保存受保护的当前 Compose 与环境配置快照，并记录每个服务实际运行镜像的不可变标识。不能只保存一个 API_IMAGE 值代替全部服务版本。
- 含配置的快照不得提交 Git，不打印凭据；保留当前版本与至少一个已验证可回滚版本。
- 流程变更在隔离测试环境试验；生产第一轮不得让新旧调度器混用同一套配额状态。先使配置/状态格式向后兼容，按已验收的协调方式切换。需要停止或重启服务时按用户规则取得明确确认。
- 服务器正常发布仅拉取指定镜像、更新服务、健康检查。参考 docs/local-production-deploy.md；不要无审查地运行任何可能包含额外清理、停止服务或迁移的脚本。
- 健康检查包括容器状态、应用接口、有限量日志、真实业务完成数量和结果质量；不能只看容器 healthy。

### 10.4 回滚交付要求

每次发布前由执行人生成已填入真实绝对路径与服务名的回滚命令，并验证配置有效。以下为命令模板，不是已经存在的快照：

```bash
docker compose --project-name image-intelligence --project-directory /opt/image-intelligence --env-file /ABSOLUTE/ROLLBACK/release.env -f /ABSOLUTE/ROLLBACK/compose.yml pull SERVICE_NAME
docker compose --project-name image-intelligence --project-directory /opt/image-intelligence --env-file /ABSOLUTE/ROLLBACK/release.env -f /ABSOLUTE/ROLLBACK/compose.yml up -d --no-deps SERVICE_NAME
docker compose --env-file /opt/image-intelligence/.env.production -f /opt/image-intelligence/docker-compose.prod.yml ps
```

执行前必须将大写占位符替换为已核实值；快照中的服务镜像必须已经固定到该服务旧版本。相互依赖的 API/worker 调度变更应列全相关服务，不能只退回一个 worker；验证配置文件的相对路径、网络及卷仍指向原项目。配置回滚同时恢复活动配置来源，防止下一次发布又读到新值；该具体操作在发布前根据真实快照生成，不临时猜路径。

不删除业务数据、不撤销已完成结果。队列与缓存格式需要兼容上一版；做不到兼容则该候选不得上线。SSH 断连、资源越界或异常发生时立即停止自动流程，先诊断，不反复执行发布或回滚。

2026-09-07 用户追加要求：优化过程中确保接口通畅，支持自动化运行。
