# 源码挂载部署方案

## 目标

这套模式保留固定的后端、前端运行时镜像，服务器更新业务时只做：

1. 从 GitLab 快进拉取代码；
2. 在宿主机编译前端静态文件；
3. 执行数据库迁移；
4. 将本次提交的源码目录只读挂载到容器；
5. 强制重建业务容器进程以加载新代码。

整个更新流程不会执行 `docker build`，也不会拉取镜像。原有的
`docker-compose.prod.yml` 镜像发布方式保持不变。

## 为什么不能只执行 restart

后端是 Uvicorn 和 Celery 常驻进程，Python 模块在进程启动时加载。即使宿主机文件已变化，
`docker restart` 也不负责更新 Compose 挂载配置。部署脚本会执行 `docker compose up` 的
`--force-recreate`，确保每个 API、Worker 和 Beat 进程都加载同一个 Git 提交。

前端源码不能直接交给 Nginx，React/TypeScript 必须先生成 `frontend/dist`。本方案在服务器
宿主机执行 `npm ci`、测试和 `npm run build`，但不构建 Docker 镜像。若服务器不允许安装
Node.js，应改由 GitLab CI 生成并下发 `dist` 产物。

## 一次性准备

服务器需要安装 Git、Docker Compose、Node.js/npm、curl，并提前导入固定运行时镜像。

在 `.env.production` 增加：

```dotenv
API_RUNTIME_IMAGE=image-intelligence-api:development
WEB_RUNTIME_IMAGE=image-intelligence-web:development
```

如果网关、分类或渲染确实使用不同依赖，可另外设置：

```dotenv
API_GATEWAY_RUNTIME_IMAGE=your-api-gateway-runtime:version
CLASSIFICATION_RUNTIME_IMAGE=your-classification-runtime:version
RENDER_RUNTIME_IMAGE=your-render-runtime:version
```

确认这些基础镜像与当前代码的依赖和模型完全一致后，初始化运行时兼容锁：

```bash
cd /opt/image-intelligence
bash scripts/deploy-source-checkout.sh --initialize-runtime-lock
```

这个操作只应在基础镜像经过验证后执行。兼容锁会记录 Python 依赖、基础 Dockerfile 和模型
清单的哈希。如果后续提交改变这些文件，普通源码发布会停止，避免用旧依赖运行新代码。

## 日常更新

运维在服务器执行：

```bash
cd /opt/image-intelligence
bash scripts/deploy-source-checkout.sh
```

脚本内部会执行 `git pull --ff-only`。若运维已经手动拉取，可使用：

```bash
bash scripts/deploy-source-checkout.sh --no-pull
```

每个提交会生成独立目录：

```text
.source-deploy/releases/<完整 Git SHA>/
```

容器挂载的是这个不可变目录，而不是正在被 `git pull` 修改的工作区。因此拉取、前端编译或
Compose 校验失败时，当前容器仍继续使用旧版本。

## 哪些修改不需要构建镜像

- `src/` 后端业务代码；
- `profiles/` 业务规则；
- `assets/` 业务资源；
- `scripts/` 应用运维脚本；
- `alembic/` 数据库迁移；
- `frontend/src/` 和 Nginx 配置，前提是服务器可执行 npm 构建。

以下修改必须先制作并导入新的基础运行时镜像：

- `pyproject.toml` 或 `requirements-redaction.txt`；
- Python/系统依赖、CUDA/ONNX/OpenVINO 等运行环境；
- 镜像内模型及其清单；
- `Dockerfile`、`Dockerfile.api`、`Dockerfile.base` 中的运行时配置。

## 回滚

成功发布后，当前版本记录在：

```text
.source-deploy/current-commit
.source-deploy/current-release
```

源码目录会保留，可用旧目录重新执行 Compose。数据库迁移是否允许降级必须单独评估，不应
自动执行 `alembic downgrade`。例如仅回滚应用代码：

```bash
export SOURCE_RELEASE_ROOT=/opt/image-intelligence/.source-deploy/releases/<旧 Git SHA>
docker compose --env-file .env.production \
  -f docker-compose.prod.yml -f docker-compose.source.yml \
  up -d --no-build --pull never --force-recreate --no-deps \
  api worker-control worker-callback worker-preprocess worker-classification \
  worker-beautify-plan worker-redaction worker-inpaint worker-enhance worker-render \
  worker-analysis worker-openclip worker-library worker-matching worker-cleanup \
  celery-beat web
```

生产回滚前应先确认新迁移对旧代码向后兼容，并保留脚本生成的数据库备份。
