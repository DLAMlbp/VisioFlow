# 公平调度候选：实现范围与验收

2026-09-07。状态：本地候选实现，默认关闭，未发布。线上质量基准及端到端提速验收仍未完成。

## 本次实现

- 增加 `AI_FAIR_SCHEDULER_ENABLED=false`，必须同时启用原有全局调度才生效。现有实际环境文件及线上参数没有修改。
- 无论使用哪种调度，记录 `vision_scheduler_wait_reason_ms`，区分 rpm、concurrency、cooldown、fairness。它们测量每次观察到阻塞后实际睡眠的时长；多个条件可同时成立，不能相加当作总等待，也不是精确到每毫秒的上游状态追踪。原有总等待和请求耗时指标保留。
- 候选通过 Redis Lua 原子执行等待登记、容量检查和领取。分类、规划、分析及其他操作按阶段轮转，同阶段按入队序号排序，空阶段可跳过。最早入队者等待超过 15 秒后优先领取，避免长期等待。
- 等待期间按轮询刷新 15 秒租约，失联条目在后续领取时清除。最多 256 个等待条目，超出时失败，不驱逐已有任务。该数量是安全边界，不是建议并发数。
- 正常公平等待轮询 250 ms；冷却期间最多间隔 1 秒。仍保留 Celery Worker 等待占用，不引入任务挂起重发，不改变多图分析的组批规则。
- 沿用旧的 RPM、在途、冷却和降容键；重复 EVAL 不会重复占额。正常返回或请求异常后释放在途名额，保留 RPM 消耗。
- 等待协程取消时移除自己的条目；领取响应丢失时保守清理可能已取得的在途名额，并保留已扣减的 RPM，不自动重发 AI 请求。
- 已开始的线程调用无法靠取消协程停止。候选在该情形保留原在途租约，待到期回收，避免立即释放导致额外请求进入；代价是异常后的短期容量可能降低。

第一轮没有改变模型、提示词、输入尺寸、标签策略、阈值、图片编码、图片处理分支、入口额度或 Worker 数量。

## 必须明确的行为边界

默认关闭时，Redis 不可用仍沿用既有的直接请求行为。**候选开启后，领取阶段 Redis 错误会阻止本次 AI 调用并向上抛出错误，不继续无保护请求。** 这是明确的异常语义差异：扩并发时优先避免突破共享额度，但不能宣传 Redis 故障下仍保证业务成功。需在启用验收中检查错误上报、恢复和接口表现。

当前在途租约仍采用原有 `AI_TAGGING_TIMEOUT_SECONDS + 30` 秒，不新增长请求续约；本项不能证明异常长时间 HTTP 调用或长时间 Redis 故障时严格保持并发上限。真实运行需验证请求截止时间与租约关系。

本次“取消”测试指等待/执行协程取消。业务 `job` 的取消检查仍沿用各 Worker 既有实现，不能用协程测试代替取消整个业务任务的端到端验收。

新旧算法共享容量账本，可以保持回退时已消耗额度，但旧算法不会遵守新等待顺序。不得混合启用模式后宣称公平性成立。公平性针对已进入调度器的请求，不能代表还在 Celery 队列中的全部图片公平性。

## 已建立的验证

`tests/integration/test_vision_fair_scheduler.py` 使用真实 Redis 和本地固定响应，不调用上游 AI。覆盖并发原子领取、RPM、共享冷却和降容、阶段轮转、同阶段先后顺序、长等待优先、心跳、失联清理、等待上限、重复 EVAL、响应丢失、取消、回退共享容量及响应对象原样返回。

测试仅允许连接 loopback Redis，使用独立随机命名空间，不运行 FLUSHDB，结束后仅缩短该命名空间的 TTL。未设置环境变量时跳过 Redis 集成测试；CI 已配置独立 Redis 服务并显式传入地址。

本次实测完整后端 428 项测试通过（59.39 秒，1 项既有 Starlette 弃用警告），其中包含 16 项真实 Redis 集成测试。结果保存在 `artifacts/time-optimization/20260907/candidate-tests.xml` 和同名 `.log`。全仓 CI 所用 Ruff 检查通过；为了解除已有阻断，仅删除了 `cover_score.py` 的一个多余空行，并调整 `processing.py` 的两行导入顺序。CI YAML 已解析核验；远程 CI 与镜像构建尚未实际运行。

独立测试 Redis 使用本地已有镜像 `sha256:71da9275c5f3fcb97d0fa0c8c5b36cc995327265420f17a04bfd544f458059f7`，容器名 `time-opt-fair-redis-user-20260907`，内存限制 64 MiB、CPU 限制 0.25，只监听本机映射端口。该容器保留运行，未改已有 Redis。首次测试容器因删除 capabilities 后入口脚本无法切换用户而退出；查明原因后，新容器显式使用非 root 用户和 Redis 入口启动成功，未发生 OOM，未删除失败容器。

本地使用独立测试容器实际映射端口后运行，例如本次端口为 57966：

```powershell
$env:TIME_OPT_TEST_REDIS_URL='redis://127.0.0.1:57966/0'
.venv/Scripts/python.exe -m pytest tests/integration/test_vision_fair_scheduler.py tests/unit/test_vision_rate_limit.py -q
```

上述验证证明调度组件的被测行为，不代表真实模型输出一致、图片质量验收通过或整批 P95 已降低。仍需固定人工标注集、同版本基线、实际请求时段和负载分布完成原计划验收。

## 启用与回退条件

1. 先运行本地/CI 完整回归及真实 Redis 测试。本地检查已通过，远程 CI 与镜像验证仍需完成；不能仅用本地测试结果声称 CI 已通过。
2. 隔离环境比较关闭/开启候选；全局仍为 5 并发、24 RPM，分类/规划/分析仍为 4/2/2，模型输入和质量参数不变。
3. 比较每阶段等待 P95、最老等待时间、批次 P95、成功产出、每张 AI 调用数、质量结果及取消/失败/恢复/回调。不得仅凭短请求模拟结果估算生产提速比例。
4. 完成业务取消、异常长请求及 Redis 故障端到端验证，再决定候选是否达到启用条件。
5. 发布前重新执行用户规定的全部资源检查。2026-09-07 12:14 的服务器 MemAvailable 为总内存的 24.81%，低于 25% 下限，不能据此继续发布或扩并发。
6. 通过后以不可变镜像协调所有参与 AI 请求的 Worker 使用相同模式。需要停止服务时按用户要求取得明确确认。按原计划记录版本化配置、镜像和精确回退命令。
7. 回退关闭 `AI_FAIR_SCHEDULER_ENABLED` 并恢复已记录的版本。保留已有额度和在途记录，不清空 Redis，不删除业务结果；实际执行须经过发布前检查及原计划的协调流程。
